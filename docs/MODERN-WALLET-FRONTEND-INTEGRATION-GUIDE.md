# Modern Wallet Frontend Integration Guide

This document is the implementation contract for the Worldstreet modern embedded wallet. The modern wallet is self-custodial: signing keys are generated and encrypted locally in the browser. The crypto backend stores wallet metadata and encrypted ciphertext, but it must never receive a plaintext private key or recovery secret.

## 1. Wallet modes and migration rules

The dashboard must support two wallet modes:

- **Modern Worldstreet wallet**: the default for new users. It supports the supported chains, local signing, wallet passphrase unlock, recovery-secret recovery, exports, transfers, swaps, spot trading, and futures trading.
- **Legacy Privy wallet**: retained for existing users and existing balances. Do not remove its UI or break its existing signing and trading flows.

Newly created Clerk users must not be provisioned a new legacy Privy wallet. Existing users may continue using their existing Privy wallet, but the product should guide them to move funds into their Worldstreet embedded wallet.

The wallet selector must make the active mode obvious. Every balance, deposit, withdrawal, transfer, and order request must include the selected wallet mode so a modern action cannot accidentally use the legacy wallet.

## 2. Required user messaging

On login, show a dismissible migration notice to users who have a legacy Privy wallet:

> Your legacy wallet is still available. For the new Worldstreet self-custodial experience, move your funds to your Worldstreet embedded wallet. You control the keys, and signing happens locally on your device.

Show the same notice in notifications until the user dismisses it or confirms that migration is complete. Never imply that Worldstreet can recover or access the user’s private keys.

Do not show this migration notice to users without a legacy wallet or to newly created users.

## 3. Wallet creation flow

The modern wallet setup should be a familiar, legacy-style guided flow:

1. User selects **Create Worldstreet wallet**.
2. Generate the wallet key material locally in the browser.
3. Create/provision the backend wallet account using the authenticated Clerk session.
4. Encrypt the local wallet package with the user’s wallet passphrase.
5. Generate the recovery secret locally and show it once in a blocking modal.
6. Require the user to confirm that the recovery secret was saved before completing setup.
7. Upload only encrypted wallet metadata/package data.
8. Display the wallet addresses for each supported chain.

The recovery modal must not be skipped silently. It should provide copy/download controls, a warning that the secret cannot be regenerated by Worldstreet, and a confirmation checkbox. Do not log or send the recovery secret to the backend.

## 4. Unlocking and signing

The normal unlock path is:

1. User enters the wallet passphrase.
2. Frontend downloads the encrypted package.
3. Frontend decrypts it locally.
4. The decrypted key material remains in memory only for the active session.

The recovery path uses the recovery secret to unwrap/reconstruct the local encryption key. The passphrase and recovery secret are separate credentials. A new device generally requires the encrypted backup/package plus the recovery secret and the passphrase required by that package’s format.

For every transaction:

1. Request an unsigned transaction intent from the backend.
2. Display a human-readable review: chain, asset, amount, recipient, fees, sponsorship status, and expiry.
3. Require the user to approve.
4. Sign locally with the unlocked modern wallet.
5. Submit the signature through the backend intent completion endpoint.
6. Poll the intent status until confirmed, failed, or expired.
7. Show the explorer link and final transaction status.

Never send private keys, passphrases, recovery secrets, or seed phrases in an API request.

## 5. Balances and assets

Use the modern balance endpoint through the existing frontend crypto client. The response can contain multiple network results and multiple assets per network. Render:

- network name and chain icon;
- wallet address with copy action;
- native asset balance;
- token symbol, name, decimals, icon, and formatted amount;
- USD value when available;
- unavailable-provider state per network rather than failing the entire page.

Balance reads are read-only and do not require wallet unlock. Refresh only on initial page load, explicit user refresh, after a confirmed transaction, or when the user changes wallet/network context. Preserve the last successful snapshot while a refresh is in progress and show its timestamp.

The modern balance UI must not use the legacy Privy balance hook. The legacy asset page may continue using its existing data source when the legacy wallet mode is selected.

## 6. Deposits and receiving funds

The modern deposit flow should show the address for the selected network and asset. Include:

- chain/network selector;
- asset selector;
- QR code;
- copy address button;
- network mismatch warning;
- confirmation that the address belongs to the user’s Worldstreet self-custodial wallet.

For perpetual-market funding, keep the funding UI separate from ordinary wallet deposits. The user first deposits USDC to the supported chain address, then initiates the trading-account funding transfer. Show both stages and their independent statuses.

## 7. Transfers and withdrawals

The transfer ticket must support native assets and supported tokens. It must collect:

- source wallet/network;
- asset/token;
- destination address;
- amount;
- optional sponsorship choice when available.

Validate address format, amount, decimal precision, minimum balance, and network before requesting an intent. The review screen must identify the exact token contract/mint and destination. The user approves locally, then the frontend submits the signed intent and tracks confirmation.

Do not assume a token symbol uniquely identifies an asset. Use the backend market/asset ID and token address or mint internally.

## 8. Spot markets and spot orders

Modern spot markets come from the backend’s dynamic router-backed registry. The frontend must not maintain a manually hardcoded market catalogue for modern wallets.

The market response includes a stable ID, symbol, quote asset, network, venue, token identifiers, chart metadata, price, and icon when available. The frontend should:

- display provider icons with a safe monogram fallback;
- use `id` as the React key and internal identity;
- display network and quote asset clearly;
- search across the complete returned catalogue;
- show only markets marked chart-supported;
- load chart data using the returned chart symbol/provider;
- keep loading/error states separate for markets, charts, order book, and wallet balances.

For a modern EVM spot order, request an unsigned spot intent. For a modern Solana spot order, request a Jupiter swap intent. In both cases the frontend reviews, signs locally, submits the signature, and tracks the resulting transaction. A quote is not a fill; do not show an order as complete until the backend reports confirmation.

## 9. Futures orders

The futures UI must work with the modern wallet mode independently of the legacy Privy mode. It should support:

- market selection;
- buy/sell direction;
- market/limit order type where supported;
- quantity and price;
- leverage and reduce-only controls where supported;
- estimated fees and liquidation-related warnings;
- review and explicit approval;
- signed order submission;
- open orders, fills, positions, and cancellation.

The frontend should treat the backend as the source of truth for market metadata, account state, order status, and venue-specific constraints. Do not expose venue-specific implementation assumptions in shared UI labels.

## 10. Perpetual trading funding UI

Keep the following actions distinct:

- **Deposit/bridge**: move supported USDC from the user’s modern wallet into the trading account.
- **Fund/transfer**: move available funds between the user’s funding and trading balances.
- **Withdraw**: request a transfer back to a user-selected destination through the supported withdrawal flow.

Each action needs its own review, signing step if required, status timeline, retry behavior, and explorer/account reference. The UI must never imply that a bridge deposit is instant. Disable duplicate submissions with an idempotency key.

## 11. Sponsorship and gas

The frontend should display sponsorship only when the backend intent explicitly says it is available for the selected network, asset, and operation. Sponsorship is not guaranteed merely because a checkbox is present.

Show:

- “Worldstreet pays network fee” when sponsorship is accepted;
- the fallback user-paid fee when sponsorship is unavailable;
- a clear reason when the provider policy, chain, operation, or allowance does not qualify.

The frontend must never call the sponsorship provider directly with secret credentials. It requests a backend intent, signs the user operation/transaction locally, and sends the signed payload back to the backend.

## 12. Export, backup, and device changes

Export private keys only after a strong local confirmation and an explicit warning. Export is a local operation; the plaintext key must never be uploaded or logged. The UI should offer per-chain/per-account export and clearly label the network.

Encrypted backup download and restore should be available under security settings. Restore must validate package version, account ownership, checksum/integrity, and supported networks before replacing local state. Use a confirmation step because restoring can replace the active local wallet package.

## 13. Error handling requirements

Map backend error codes to actionable user messages. In particular:

- `AUTH_REQUIRED`: refresh the Clerk session and retry once.
- `WALLET_NOT_FOUND`: offer wallet setup, not a generic network error.
- `USER_VERIFICATION_REQUIRED`: explain the required local verification/recovery step.
- `INSUFFICIENT_FUNDS`: show available and requested amounts.
- `SPONSORSHIP_UNAVAILABLE`: offer user-paid gas if supported.
- `RPC_UNAVAILABLE` or provider failure: preserve the last data and offer retry.
- `INTENT_EXPIRED`: request a fresh intent; never reuse the expired one.
- `DUPLICATE_REQUEST`: display the existing operation status.

Do not label authentication, RPC, missing-wallet, or market-catalogue errors all as “backend unreachable.”

## 14. Acceptance checklist

- New Clerk user receives only a modern Worldstreet wallet.
- Existing Clerk user can choose modern or legacy Privy wallet.
- Legacy Privy wallet remains functional and unchanged.
- Login and notifications show migration guidance only when applicable.
- Recovery secret is shown and acknowledged during creation.
- Modern balances show native assets and tokens with icons and network labels.
- Modern market list uses backend registry IDs, provider icons, and chart-supported markets.
- Modern transfers support native assets and tokens.
- Spot and futures orders use review → local sign → submit → status flow.
- Perpetual-account deposit, funding transfer, and withdrawal are separate flows.
- Sponsorship availability is reported by the backend and never assumed.
- No plaintext key, passphrase, recovery secret, or provider secret reaches the backend or browser logs.
